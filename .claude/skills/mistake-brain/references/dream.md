# dream.md — reflect across the whole memory

Invoked by `/mistake-brain dream`, name and spirit borrowed from [agent-brain](https://github.com/renenel/agent-brain)'s `dream` command. Unlike `log`/`route`/`promote`, which each process one thing at a time, `dream` is a periodic, zoomed-out pass over the *entire* memory. Run it occasionally — end of a long session, when MEMORY.md feels out of date, or when the user asks for a "reflection" — not after every failure.

## Why this is separate from `route`/`promote`

`route` and `promote` are reactive and local: they look at one new entry, or one repetition group, in isolation. `dream` is the only pass that looks at the *shape* of the whole memory — whether Areas have grown too broad, whether a Project is actually done and should archive, whether the same Resource-worthy principle is showing up scattered across multiple Area files without anyone noticing. That kind of pattern is invisible from inside a single `route` or `promote` run.

## Procedure

1. Read `.claude/agent-memory/<agent>/MEMORY.md` fully — it lists a last-updated date per PARA file and, at the bottom, the date of the last dream pass. Only fully read files whose last-updated date is newer than the last dream date (or that have never been dreamt over yet); for everything else, trust MEMORY.md's existing one-line summary rather than re-reading a file that hasn't changed since you last looked at it. This keeps a dream pass proportional to what's actually changed, not to the total size of the memory. Also `Grep` `MISTAKES.md` for `^- \*\*Status:\*\*\s*unrouted\s*$` (same targeted approach and same anchored pattern as `router.md`, not a full read) to flag any pending routing without loading the whole log — this catches unrouted entries of every `Type`, not just mistakes.

   For each match from that grep, also check its `Type` field (in the same `-B 5` context block): for any that are `Type: handoff`, compare the entry's own header date to today. This is the same reasoning as the heartbeat check in step 2, applied per-entry instead of per-file — a stale, unrouted handoff is worse than a stale mistake, since a handoff exists specifically so a *different* session can pick up context that would otherwise be lost, and an unrouted one is sitting nowhere a fresh session would think to look. A gap of **7+ days** (same threshold as the file-level heartbeat, for consistency) is a finding — see step 3.

2. **Heartbeat check — is logging even happening?** Run `git log -1 --format=%cd --date=short -- MISTAKES.md` from the repo root. If it returns nothing, this is a repo with no commit history yet touching the file — skip this check, that's the cold-start case already covered in README.md, not a heartbeat problem. If it returns a date, compare it to today: if the gap is **7+ days**, this is a real finding, not silence to pass over — see step 3 below. The reasoning: `route`/`promote`/`dream` have no independent way to discover a mistake happened. If `log` never fires — a skill-trigger miss, or nobody remembered to run it manually — the entire chain stays frozen, not degraded, and a `dream` pass that finds "nothing new" looks identical whether that's because things are genuinely fine or because logging silently stopped weeks ago. This check is what tells those two cases apart.

3. Look for, and note as findings (don't act on any of these without asking — see below):
   - **Heartbeat**: if step 2 found a 7+ day gap since `MISTAKES.md` was last touched, report it explicitly and by name — e.g. "no log activity in 12 days — worth checking whether `/mistake-brain log` is actually being run, or whether the skill just hasn't triggered." Never silently fold this into "no findings"; a quiet log is a distinct, reportable state from an actively-maintained one that simply has nothing new.
   - **Stale handoffs**: any `Type: handoff` entry step 1 flagged with a 7+ day gap since its own header date, still sitting `unrouted` (or otherwise unactioned). Report each by date and title — e.g. "handoff from 12 days ago ('Mid-refactor: auth token refresh migration') is still unrouted — confirm it's stale before letting it sit longer, since a handoff is meant to be picked up quickly, not archived silently." This is deliberately the same detection shape as the file-level heartbeat (a date-gap check), not a new write-on-read `consumed` status — see `format-spec.md`'s `handoff` section and `SKILL.md`'s Concurrency section for why that was rejected.
   - **Stale Projects**: a Project file whose project appears finished, merged, or abandoned (no recent related activity, or the user mentions it's done). Candidate to move to Archives, or to Areas if its lessons turned out to be general rather than project-specific. Use each entry's `Added` timestamp (see `router.md` step 4), not just `MEMORY.md`'s per-file last-updated date, to tell "this whole file is old" apart from "this file just has one recent entry sitting on top of an otherwise-stale pile" — the latter looks fresh at the file level but isn't, entry by entry.
   - **Oversized or fragmented Areas**: an Area file that's grown long enough to be hard to skim, or the same domain split unnecessarily across two files. Candidate to split or merge. `Added` timestamps can also surface a split candidate MEMORY.md's summary wouldn't: a burst of entries added in one narrow window vs. a steady trickle over months often means two different sub-topics got lumped into one file.
   - **Cross-cutting principles**: the same underlying lesson appearing independently in two or more different Area/Project files. This is exactly the pattern that should have become a Resource — surface it as a candidate.
   - **Promotion candidates**: run `scripts/check_repetition.py` as part of this pass too (dream is a good time to catch repeats that individual `promote` runs might have missed since MEMORY.md was last updated).
   - **Contradictions**: two lessons that give conflicting guidance. Flag explicitly — don't silently pick a winner.

4. Regenerate MEMORY.md's index sections (Projects/Areas/Resources/Archives one-liners, lesson counts, last-updated dates) to match current reality — this part you can just do, since MEMORY.md is derived/summary data, not a source of truth in itself. Add a `## Last dream` entry at the bottom with today's date and a short summary of what you found, including the heartbeat result from step 2 even when it's clean (a dated "logging active as of <date>" is itself useful signal for the next dream pass, not just the gap case).

5. Present the findings from step 3 to the user as a numbered list of proposed actions (archive this, merge these two, split this, promote this — and, for a heartbeat gap, "check why logging stopped"). Ask which ones to act on — this is the same confirmation posture as `promote.md` for anything that would move or delete content in `.agent-brain/`, and the mandatory posture for anything touching `CLAUDE.md`/`.claude/rules/`. Regenerating MEMORY.md's own summaries (step 4) doesn't need confirmation; restructuring the underlying PARA files does.

6. Only make the changes the user actually approves, then re-run step 4 to reflect the result.

## What "good" looks like

A useful dream pass ends with MEMORY.md being something a future session could read cold and immediately know where to look — not a bigger pile of unreviewed suggestions. If a dream pass surfaces the same "you should really split Areas/ci.md" finding three times in a row without the user acting on it, that's worth mentioning plainly rather than re-surfacing silently forever.
